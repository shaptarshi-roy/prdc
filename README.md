# P-RDC MDS-PT ingest stack

One-way pipeline for MDS-PT treatment-episode batches. The
**Datentreuhandstelle (DTS)** is the only submitter: it POSTs CSV batches
over mTLS on behalf of all participating facilities. API Platform accepts
each batch, a background worker runs it through six validation gates, and
accepted rows land in Postgres. Quarantined rows return only as metadata —
no patient payload ever leaves.

## Who submits what

- **One submitter.** Only the DTS holds a client certificate and a
  submission JWT. Facilities never talk to this stack directly.
- **Batches are multi-facility.** A single batch may contain rows from any
  number of facilities. The `facility_id` column *in each row* names the
  facility where the treatment took place; it is validated for format
  (gate 0) and consistency (gates 4–5), not matched against the submitter.
- **`batch_log.facility_id` is the submitter**, not a facility. It records
  which authenticated identity uploaded the batch, and the status/errors
  endpoints only show a batch to that same identity. With the DTS as sole
  submitter, the DTS sees all batches.
- **Dev identity naming.** The dev setup represents the DTS with the
  placeholder user `facility_f008` and client cert `F008.crt`. The names
  predate the single-submitter model; they are just the DTS's dev identity.

## Services

| Service | What it does                                                    |
|---------|-----------------------------------------------------------------|
| `proxy` | Caddy; terminates TLS, verifies the DTS client cert, forwards to PHP-FPM over a Unix socket |
| `api`   | API Platform (Symfony); accepts batches, exposes status/errors  |
| `worker`| Same image as `api`; runs the Messenger consumer (validation) and the daily file purge |
| `db`    | Postgres 17 with the MDS-PT schema and roles from `db/init/`    |

### Network and access boundaries

- Only `proxy` publishes a host port (443; port 80 in dev HTTP mode).
- `proxy` reaches `api` **only** through the shared `fpm_socket` volume —
  there is no network link and FPM has no TCP listener.
- `api` and `worker` are on separate internal networks (`api-db`,
  `worker-db`) that both reach `db` but not each other or the internet.
- Each container uses its own least-privilege database role:

| Role          | Can do                                                                  |
|---------------|-------------------------------------------------------------------------|
| `api_role`    | Insert `batch_log` rows; read `batch_log` + `quarantine`; enqueue jobs (`INSERT` + `SELECT (id)` on `messenger_messages`). **No access to data tables or researcher views.** |
| `worker_role` | Write the six data tables and `quarantine`; update `batch_log` status; consume jobs from `messenger_messages`. Cannot create batches. |
| `researcher`  | Read-only on the researcher views (`03-researcher-views.sql`).          |

No role can `CREATE` in the schema. The Messenger queue table is created
by `db/init/01-schema.sql`, and both transports use `auto_setup=0`.

## First-time setup

Run from the repository root. Every secret is generated and written to a
file — nothing is typed at an interactive prompt, so nothing gets lost.

```bash
# 1. Database passwords — all four are required by docker-compose.yml
for s in db_password api_db_password worker_db_password researcher_db_password; do
  openssl rand -hex 32 > "secrets/$s.txt"
done
chmod 600 secrets/*.txt

# 2. App secrets — set APP_SECRET and JWT_PASSPHRASE in api/.env
#    (the app reads api/.env; the root .env is not used).
#    Generate values with: openssl rand -hex 32

# 3. JWT keypair, encrypted with the JWT_PASSPHRASE from api/.env
export JWTPW="$(grep -E '^JWT_PASSPHRASE=' api/.env | cut -d= -f2- | tr -d \"\'\")"
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 \
    -aes-256-cbc -pass env:JWTPW -out api/config/jwt/private.pem
openssl pkey -in api/config/jwt/private.pem -passin env:JWTPW \
    -pubout -out api/config/jwt/public.pem
unset JWTPW

# 4. Dev CA + DTS client cert — see caddy/README.md

# 5. Build and start (production layout: HTTPS + mTLS on 443)
docker compose build
docker compose up -d
```

The database schema, roles and queue table are created on the **first**
start of an empty `pgdata` volume. Changing `db/init/` later has no effect
on an existing database; apply the change by hand or reset the volume with
`docker compose down -v` (this deletes all data).

### Dev mode: plain HTTP on port 80

For testing the api/worker/db without certificates:

```bash
docker compose -f docker-compose.yml -f docker-compose.http.yml up -d --build
```

This swaps in `caddy/Caddyfile.dev` and publishes `0.0.0.0:80` instead of
443. mTLS is off, so any client-sent `X-Client-Cert-*` headers are
stripped. The JWT is still required. **Never deploy this override.** Use
`127.0.0.1:80:80` in it if only the local machine needs access.

## Getting a dev JWT

```bash
JWT=$(docker compose exec -T api php bin/console \
        lexik:jwt:generate-token facility_f008 | grep '^ey')
```

Tokens are valid for one hour (`token_ttl` in `lexik_jwt_authentication.yaml`).

## Submitting a batch (DTS)

Production (mTLS on 443):

```bash
curl --cert caddy/F008.crt --key caddy/F008.key --cacert caddy/ca.crt \
     -H "Authorization: Bearer $JWT" \
     -F "batch=@episode.csv;type=text/csv" \
     https://localhost/batches
```

Dev HTTP mode: same request without the `--cert/--key/--cacert` options,
against `http://localhost/batches`.

Response (`202 Accepted`):

```json
{"batch_id":"018f5d3e-7bef-7d12-a831-16e2b6e78c9f","status":"received"}
```

The `batch_log` row and the validation job are written in one
transaction: if the job can't be queued, the request fails, nothing is
recorded and the uploaded file is removed, so the DTS can safely resubmit.

## Polling for completion

```bash
BATCH=018f5d3e-7bef-7d12-a831-16e2b6e78c9f

curl --cert caddy/F008.crt --key caddy/F008.key --cacert caddy/ca.crt \
     -H "Authorization: Bearer $JWT" \
     https://localhost/batches/$BATCH/status
```

`GET /batches/{id}/errors` returns the per-row quarantine report (row
index, gate, error code, field — never the row contents).

Observable states:

| status               | meaning                                                       |
|----------------------|---------------------------------------------------------------|
| `received`           | on disk, queued for validation                                |
| `validating`         | worker has picked up the job                                  |
| `completed`          | all rows written                                              |
| `partial_quarantine` | some rows written, some rejected — see `errors_url`           |
| `blocked_for_review` | gate 5 collision — human review required, no auto-resubmit    |
| `failed`             | pipeline crashed                                              |

The OpenAPI document is served at `/docs.json` (no Swagger UI).

## Raw file retention

The worker runs `app:purge-batch-files` daily at 03:17 UTC
(`api/docker/run-purge.sh`, under supervisord as the non-root `app` user).
It deletes raw CSVs of batches in a terminal state older than
`BATCH_RETENTION_DAYS` (default 30). `batch_log` rows are the audit trail
and are never deleted. Override the run time with `PURGE_AT=HH:MM`.

## Adding a gate

1. Create a class in `api/src/Validation/Gate/` that implements `ValidationGateInterface`.
2. That's it — `services.yaml` tags it via `_instanceof` and the pipeline sorts by `number()`.

## Regenerating the schema

When the codebook changes:

```bash
python3 tools/generate_schema.py \
    --adult    MDS_Adult_codebook.json \
    --pt       MDS_PT_codebook.json \
    --mapping  tools/mapping.json \
    --out      db/init/01-schema.sql
```

The generator also emits the roles, grants and Messenger queue table, so
edit those in `generate_schema.py`, not only in the generated file. Then
rebuild the database for a fresh environment, or write a Doctrine
migration for a non-destructive update in production.

## Known gaps

- **Client cert not bound to the JWT.** Caddy requires a valid client
  cert, but the app authenticates only by JWT and ignores the forwarded
  `X-Client-Cert-*` headers. It should check that the cert is the DTS's.
- **Secrets baked into the image.** `api/.env` (`APP_SECRET`,
  `JWT_PASSPHRASE`) and the JWT private key are copied into the image at
  build time; they should be mounted at runtime as Docker secrets.
- **Composer advisory blocking is disabled** (`config.policy.advisories.block: false`
  in `api/composer.json`).
- **No researcher endpoints yet.** The `/researcher` firewall, access rule
  and Caddy route exist, but no routes are implemented.
